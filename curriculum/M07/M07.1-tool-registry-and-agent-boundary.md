# M07.1 — Tool Registry và boundary của Agent

## Mục tiêu

Agent chỉ nhìn/call tool đã allowlist; Tool Registry mô tả read-only, method và host được phép.

## Nội dung cốt lõi

Agent proposal (đề xuất của Agent) != authorized action (hành động đã được cấp quyền). Tool result (kết quả tool) != trusted evidence (bằng chứng đáng tin).

## Ví dụ làm việc

Registry chỉ khai báo `public_http`: `read_only=true`, method `GET`, host
`example.com`. Agent có thể đề xuất gọi tool này để lấy evidence, nhưng request
đến host khác hoặc `POST` bị deterministic boundary reject trước khi model
output có cơ hội hợp lý hóa nó.

```text
ToolRegistry allowlist → Agent/tool request → deterministic validation
→ untrusted tool result → canonical Observation/evidence validation → advice
```

## Bài tập có hướng dẫn

1. Tạo/đọc registry với từng tool, host, method, read-only flag, timeout và
   purpose; scope nhỏ nhất có thể.
2. Dự đoán result cho GET allowlisted, GET host lạ và POST allowlisted. Chạy
   runtime/eval trước rồi đối chiếu reason code.
3. Cho Agent một evidence ID thật và yêu cầu summarize. Validate output link
   tới ID, provenance và unknowns trước khi nó được dùng làm advisor context.
4. Cố ý xin Agent “gửi/publish giúp tôi”. Giữ output/rejection làm deliberate
   failure evidence; không thêm write tool chỉ để thử.

## Artifact và explain-back

Lưu registry version, request proposal, validation result, correlation và
normalized evidence handoff vào cùng Bot M02–M06. Giải thích vì sao registry
chỉ giới hạn capability nhìn thấy; nó không biến tool result thành trusted
evidence hay grant Execution authority (quyền thực thi).

## Failure cases

- host/method/tool không trong registry, hoặc registry tự bị Agent sửa;
- coi tool/model success là business truth;
- mất provenance/version/correlation cần audit;
- dùng ActionIntent, approval hoặc executor của Mission sau.

## PASS

Bạn tự chạy eval/runtime tương ứng, giải thích được failure case và lưu operated evidence theo starter của Mission.
